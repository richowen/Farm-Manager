# PWA Photo Viewer + Hardware Back Button Fix

## The problem

1. **Primary bug.** Uploaded photos on events (`EventRow.svelte:96-104`) and on pins (`PinDetailSheet.svelte:202-210`) are rendered as
   ```html
   <a href={`/uploads/${p.path}`} target="_blank" rel="noopener">
   ```
   In a standalone PWA on Android/iOS, `target="_blank"` hands the image to the system browser. The user sees the raw photo with no in-app chrome, and pressing the hardware back button dismisses the PWA instead of returning to the photo's context. There is literally no way back to the task/pin.

2. **Secondary bug (same root cause).** Every in-app overlay (pin detail sheet, location detail panel, pin drop modal, new-location modal, batch event/property forms, I-Am-Here chooser, task editor) calls `incrementOverlay()` / `decrementOverlay()` but none of them register a history entry. So the hardware back button exits the PWA whenever any overlay is open, even though the user intuitively expects back to dismiss the overlay first.

The `PhotoInput` component (`src/lib/components/PhotoInput.svelte:100-111`) already has an in-app lightbox for the edit form — we can generalise it, then wire every overlay (lightbox included) into a single back-button handler.

## Success criteria

- Tapping a photo on a pin or event opens a full-screen lightbox **inside** the PWA with a visible close button (X), backdrop tap, and Escape key all dismissing it.
- Hardware back / browser back on Android closes the lightbox when it's open, without exiting the PWA.
- Same behaviour for: pin detail sheet, location detail panel, pin drop modal (create/edit), new-location modal, batch property/event forms, I-Am-Here chooser, task editor dialog. Back dismisses the top overlay; only when no overlay is open does back exit or navigate away.
- Closing an overlay via its own UI (X, Cancel, backdrop) consumes exactly one history entry (so a user pressing back once after an in-UI close doesn't land on a stale overlay state).
- Mobile nav hiding (`overlayCount`) continues to work unchanged.
- Photos inside the `PhotoInput` edit control continue to open the lightbox (unified through the new component).
- Desktop behaviour is unchanged: Escape closes, backdrop click closes, X button closes.
- No regressions to the existing Playwright tests.

## Design

### 1. New overlay history helper — `src/lib/utils/overlay.ts`

A tiny module that owns a stack of open overlays and bridges them to `history.pushState` / `popstate`, while preserving the existing `overlayCount` writable.

```ts
import { overlayCount } from '$lib/stores';

interface Entry { id: number; close: () => void; }
const stack: Entry[] = [];
let nextId = 1;
let suppressNextPop = false;
let installed = false;

function install() {
  if (installed || typeof window === 'undefined') return;
  installed = true;
  window.addEventListener('popstate', () => {
    if (suppressNextPop) { suppressNextPop = false; return; }
    const top = stack.pop();
    if (!top) return;
    overlayCount.update((n) => Math.max(0, n - 1));
    try { top.close(); } catch (e) { console.error(e); }
  });
}

/**
 * Register an overlay. Returns a dispose function the component calls when it
 * closes itself via its own UI (X button, backdrop, Cancel, save-success).
 * Calling dispose while the overlay is at the top of the stack consumes the
 * matching history entry via `history.back()` so the user can't navigate to a
 * stale state. If the overlay is no longer at the top (already popped by
 * popstate), dispose is a no-op.
 */
export function openOverlay(close: () => void): () => void {
  install();
  const id = nextId++;
  const entry: Entry = { id, close };
  stack.push(entry);
  overlayCount.update((n) => n + 1);
  // Preserve SvelteKit's state keys so scroll restoration etc. keep working.
  const prev = (history.state ?? {}) as Record<string, unknown>;
  history.pushState({ ...prev, overlay: id }, '');

  return () => {
    const idx = stack.indexOf(entry);
    if (idx === -1) return; // already removed by popstate
    if (idx === stack.length - 1) {
      stack.pop();
      overlayCount.update((n) => Math.max(0, n - 1));
      suppressNextPop = true;
      history.back();
    } else {
      // Not at top (rare — another overlay was opened above us then already
      // dismissed). Just remove our entry; leave history untouched.
      stack.splice(idx, 1);
      overlayCount.update((n) => Math.max(0, n - 1));
    }
  };
}
```

Notes / risks:
- Known limitation: if an overlay is open and the user clicks an in-app link that triggers a SvelteKit navigation (e.g. the "in {field}" link inside `PinDetailSheet`), the overlay's history entry is orphaned below the new page. Pressing back will fire our popstate and we'll call the stored close function, but the sheet is already gone. Harmless (no-op). Document this; no behaviour change worth the complexity right now.
- `suppressNextPop` guards the "close-via-UI then history.back" round-trip so we don't double-fire the close callback.
- `install()` is guarded by `typeof window` so SSR is untouched.
- The existing `incrementOverlay` / `decrementOverlay` remain exported for any call site we don't migrate (none after this change), and `openOverlay` reuses the same store so mobile-nav hiding still works.

### 2. New `PhotoLightbox.svelte` component — `src/lib/components/PhotoLightbox.svelte`

Replaces the inline lightbox in `PhotoInput.svelte` and the broken `<a target="_blank">` in `EventRow.svelte` / `PinDetailSheet.svelte`.

Contract:
- Prop: `src: string | null` (null ⇒ not open).
- Dispatches: `close`.
- Fixed overlay `z-[3000]` (above pin sheet / detail panel / modals at `z-[1500]`–`z-[2500]`), black/80 backdrop, photo at `max-h-full max-w-full`.
- Close affordances: X button top-right (safe-area aware, `env(safe-area-inset-top)`), backdrop click, Escape key, hardware back.
- On mount (`src` transitioning to non-null) it calls `openOverlay(() => dispatch('close'))` and stores the dispose fn.
- On unmount / `src` going null, it calls the dispose fn.
- Prevent body scroll while open (add/remove `overflow-hidden` on `document.documentElement`).
- Uses `<img loading="eager" decoding="async">`. No zoom, no nav arrows (per user's choice "None — just close cleanly").

### 3. Migrate existing overlays to `openOverlay`

Each call site currently does:
```svelte
onMount(() => incrementOverlay());
onDestroy(() => decrementOverlay());
```
becomes:
```svelte
let disposeOverlay: (() => void) | null = null;
onMount(() => { disposeOverlay = openOverlay(() => dispatch('cancel')); });
onDestroy(() => { disposeOverlay?.(); });
```
(the `close` callback is whatever logic dismisses the component — for always-mounted-while-open dialogs this is `dispatch('cancel')`; for selection-driven panels it's `selectedPinId.set(null)` etc.)

Migration list:

| File | Current mechanism | New close callback |
|---|---|---|
| `src/lib/components/PinDetailSheet.svelte` | Reactive `$:` toggling on `selectedPinId` | `selectedPinId.set(null)` |
| `src/lib/components/DetailPanel.svelte` | Similar reactive block on `selectedLocationId` (see `DetailPanel.svelte:128`) | `selectedLocationId.set(null)` |
| `src/lib/components/PinDropModal.svelte` | `onMount`/`onDestroy` | `dispatch('cancel')` |
| `src/lib/components/NewLocationModal.svelte` | same | `dispatch('cancel')` |
| `src/lib/components/BatchPropertyForm.svelte` | same | `dispatch('cancel')` (or equivalent close event — confirm while editing) |
| `src/lib/components/BatchEventForm.svelte` | same | `dispatch('cancel')` |
| `src/lib/components/IAmHereChooser.svelte` | same | `dispatch('close')` / equivalent |
| `src/routes/tasks/+page.svelte` | Reactive `$:` on `showForm` | `showForm = false` |

Important rule: each close callback must be **idempotent** — safe to call when the overlay is already closing (e.g. during component teardown). The existing `decrementOverlay` is idempotent; `selectedPinId.set(null)` and `showForm = false` are also idempotent. `dispatch('cancel')` is idempotent provided the parent's handler just clears a boolean.

For the reactive `$: if (shouldBe && !overlayActive) { ... }` blocks in `PinDetailSheet` and `DetailPanel`, we keep the same gate but swap `incrementOverlay()` → `openOverlay(...)` and store the dispose fn instead of a boolean. `onDestroy` calls the dispose fn.

### 4. Replace photo links with the lightbox

- `src/lib/components/PhotoInput.svelte`: delete inline lightbox markup & `openLightbox` state; import & mount `PhotoLightbox` bound to a local `lightboxSrc`.
- `src/lib/components/EventRow.svelte:93-106`: replace `<a href target="_blank">` thumbnails with `<button type="button" on:click={() => (lightboxSrc = `/uploads/${p.path}`)}>`; mount one `<PhotoLightbox bind:src={lightboxSrc}>` at the component root.
- `src/lib/components/PinDetailSheet.svelte:199-212`: same pattern. Because the sheet itself is now an overlay with back-button wiring, opening the lightbox stacks a second history entry — back will close lightbox first, then the sheet, then exit. This is the target UX.

### 5. Small UX polish (non-risky)

- Lightbox close button positioned inside `env(safe-area-inset-top)` so it's reachable on iPhone notches.
- Add `aria-label="Close photo"` and `aria-label="View photo"` consistently.
- Lightbox traps focus on the close button on mount; restores focus to the triggering thumbnail on close (best-effort via stored `lastFocused = document.activeElement`).

No other UI changes — keep this PR focused.

## Out of scope (explicitly)

- Pinch-to-zoom / swipe between photos / download button — user opted for minimal close-cleanly lightbox.
- Touching `manifest.webmanifest` or service worker behaviour.
- Changing the tasks page to display photos (it currently doesn't).
- Any styling changes beyond what's needed for the lightbox close-button safe area.

## Risk and rollback

- Central risk is the `popstate` handler interacting with SvelteKit's own router. Mitigated by (a) preserving existing `history.state` fields when pushing, and (b) only popping our own stack (not synthesising a navigation). If a regression slips through, rollback is limited to `src/lib/utils/overlay.ts`; call sites can temporarily revert to `incrementOverlay`/`decrementOverlay` without touching the photo-viewer change, since those remain exported.
